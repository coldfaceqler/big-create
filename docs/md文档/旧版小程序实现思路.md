# 旧版小程序实现思路

本文记录删除 `mini app/` 之前，那一版代码实际怎么做。产品范围和阶段顺序以 `重疾险条款风险批注工具-整合方案.md` 为准。重建时保留这里的处理顺序和取舍，不要把文中标明的车险残留原样搬回来。

旧版载体是微信小程序加两个云函数。页面只负责选文件、展示和提问；合同处理集中在云函数。数据存在手机本地，没有用户体系和云数据库。

---

## 1. 主路径

首页进入上传或收藏。上传页用微信的 `chooseMessageFile` 从聊天记录选 PDF，最多 20 份，单份不超过 50MB。文件先传到云存储，再调用 `analyzeContract`。返回结果写入本地键 `uploaded_contracts`，然后打开列表。列表点进详情：上半部分按标签展示条款，下半部分把条款拼成正文，调用 `contractChat` 提问。收藏只存合同 id，放在另一个本地键 `favorited_contracts`。

密钥只放在云函数环境变量 `DEEPSEEK_API_KEY`。两个云函数都调用 DeepSeek 的 `deepseek-chat`。没有密钥时，结构识别和补充分类会跳过，问答直接返回不可用。

---

## 2. 解析流水线

`analyzeContract` 固定五步。前三步在文本模块，第四步切条款，第五步分类。

```text
下载 PDF → 抽出可选中文字 → 跳过封面 → 认出章节 → 洗版式
        → 按「第X条」切开并丢掉引用 → 规则分类，少量交给模型
```

### 2.1 只接受能抽出文字的 PDF

用 `pdf-parse` 抽文本。全文少于约 500 字，就视为扫描件并失败，提示需要可选中文字的文件。这一版不做 OCR。解析本身报错时，也告诉用户文件不完整或不是可选中文本。

### 2.2 先跳过保单封面，再认章节

封面、投保单信息不是条款。代码用几个起始标记里最早出现的位置，往前留约 50 字，从那里开始往后处理。标记包括「总则」「第一条」，也还留着车险的「机动车保险条款」。

章节优先交给模型。提示词要求它列出主险大标题、一个「附加险」总标题、具体附加责任名称，以及文末释义，并且只返回 JSON。模型不可用、超时或 JSON 无效时，降级为关键词：从「第一条」切出主险，再用「附加……险」切附加险；一个附加险都没有，就整段当作主险。

模型给出的标题要回到原文里定位。从上一个标题之后继续找，避免同名标题总是命中第一次出现。两段标题之间的文字归前一个章节。标题在原文里找不到就丢掉这一节。

章节类型按标题粗分：主险、附加险、释义或定义、特约、其他。

### 2.3 清洗只动版式

清洗发生在章节切开之后，只处理排版噪音，不改语义，也不抽取字段：

- 去掉独立成行的页码、行尾残留数字、「第 X 页」、「X / Y」
- 去掉行尾的保险公司名称
- 把句中被错误换开的行拼回去；句号、分号、问号、叹号后的换行保留
- 「第X条」后面强制换行，方便下一步切割
- 压掉多余空行和空格

页码规则只认 1 到 50。超过 50 页的合同，后面的页码清不掉。把行拼回去时，也可能把本来该分开的短行粘在一起。

### 2.4 按「第X条」切，并用编号连续性丢掉引用

每一章单独切。匹配「第」加中文数字或阿拉伯数字再加「条」。中文数字先换成阿拉伯数字，目前处理到「百」。

正文里经常出现「按照第十二条」这种引用，不能当成新条款的开头。连续性规则是：

- 编号必须比上一条大。倒退的视为引用。
- 一次跳跃不超过 5。跳得更大，视为引用了别的章节。
- 这个编号前面约 30 字如果以「本条款」「按照」「依照」「根据」结尾，视为引用。
- 第一条匹配默认保留。

通过检查的位置之间的文字，就是这一条的正文，并去掉开头的冒号和空白。

某一章完全没有「第X条」，但正文不是空的，就把整章收成一条没有编号的说明。重疾合同里疾病定义常常整章都没有「第X条」，旧代码会整段收成一条，后面的分类和问答都会被这一大段拖住。附加险会先按行首的「附加……险 / 特约条款」拆成若干份，再对每一份做同样的「第X条」切割。拆分规则带有车险句式，例如标题后面紧跟「投保了」。

章节标题本身插进结果里，编号写成一行等号，标记为分隔符。分隔符不参加分类，问答时也跳过。

### 2.5 规则先分类，模型只补一小批

分类对象是非分隔符条款。标签仍是车险阅读留下的 5 类：

| 编号 | 名称 | 旧规则在找什么 |
|------|------|----------------|
| 1 | 什么能赔 | 「负责赔偿」且没有「不负责 / 不承担」，正文较长 |
| 2 | 什么不赔 | 「不负责赔偿」及相近句式 |
| 3 | 怎么理赔 | 赔款计算、索赔材料、报案、通知保险人 |
| 4 | 合同规则 | 保险金额、责任限额、保险期间、免赔、解除、变更、争议解决 |
| 5 | 其他说明 | 第一条、名词释义、很短的章节标题，以及下面没分出去的条款 |

规则没有命中的记为待分类。待分类不超过 30 条时，把每条的前 150 字交给模型，要求返回 JSON。超过 30 条就不再调用模型，全部标成「其他说明」，避免云函数超时。模型失败或返回对不上 id 的，也落到「其他说明」。

有一批规则写成了 `includes('保险人.*负责赔偿')` 这种带 `.*` 的字符串。`includes` 不做正则，这些条件实际上不会命中。真正生效的是普通关键词和 `match`。

这 5 类不能当作重疾阅读结构。等待期、疾病定义、健康告知、现金价值会被「负责赔偿」「不负责赔偿」或「其他」吸走。名词释义规则还在找「被保险机动车」「第三者」「车上人员」。

### 2.6 顺手抽取的保单信息

从全文用正则取保险公司名称、总保费，以及车牌号。车牌号是车险字段。这些信息不参与条款分类。

## 3. 云函数返回什么

成功时返回文件名、`basicInfo`、条款数组、分类计数、警告和一份 `analysis`。

每条条款保留：`id`、`number`、完整 `content`、`category`、`categoryName`、`categoryLabel`、是否分隔符、`sectionType`。内容不再截断。

有三个字段是旧功能留下的空壳，重建时不要再填假值：

- `contractText` 固定返回空字符串。详情页问答并不读它，而是用条款列表在前端再拼一遍。
- `analysis.scores` 六个维度全是 0，对应已经删除的车险偏好打分。
- `warnings` 固定是空数组。`userProfile` 原样回传，云函数不用它。

失败时 `success` 为 false，带上错误信息。扫描件会在抽文本这一步直接抛出，走到这个失败返回。

## 4. 页面怎么用这些结果

上传页对每一份文件单独调用云函数。某一份失败时，仍放进结果列表，并标 `failed`。外层只有整段流程抛错才提示「分析失败」。单份失败被收进列表之后，界面仍提示「分析完成」。这是旧版的错误提示问题。

保存时直接覆盖 `uploaded_contracts`。第二次上传不会并上第一次的合同，收藏 id 可能还指着已经不在列表里的合同。

列表只显示文件名、失败原因和收藏，不做评分、不做排序。失败原因从错误文本里认：扫描版、加密、损坏、文本过少。

详情页用本地 5 类名称再标一次条款，和云函数的 `categoryName` 可能不一致。复制全文时按条款拼。提问前把非分隔符条款按类拼成一大段 `contractText` 交给 `contractChat`，同时把条款数组也传过去，但问答云函数没有读这个数组。

问答的系统设定已经改成重疾阅读助手：只根据当前这份合同回答；优先引用条款编号、章节或疾病定义；覆盖保障责任、定义与常识差异、等待期、保额与多次或分组、健康告知、犹豫期与现金价值、免责；找不到就说明合同未写明；不编造、不推销。温度 0.2，回答长度设了上限。合同正文整段放进系统提示，没有检索，也没有法规知识库。

「我的」页只读微信头像和昵称，不参与解析。

## 5. 重建时建议留下的想法

这些是旧版里值得继续用的做法，和载体是小程序还是网页无关：

1. 处理顺序保持「抽文本 → 认章节 → 洗版式 → 按条切开 → 分类 → 再给人看或提问」。分类和问答都建立在切分质量上。
2. 扫描件明确失败。抽不出足够文字时，不要返回一份看起来分析成功的空合同。
3. 「第X条」要区分正文标题和句中引用。编号倒退、跳跃过大、紧挨「按照 / 依照 / 根据」，这三条启发式可以继续用，阈值要用重疾样本重新量。
4. 没有「第X条」的章节不能只剩「整章一条」。疾病定义、等待期、现金价值经常是这种结构，需要单独的切分策略。
5. 分类继续「规则优先，模型只处理规则吃不准的少数条款」。规则改成重疾阅读标签：保障责任、疾病定义、赔付条件、保额与多次或分组、健康告知与义务、费用与现金价值、责任免除、其他。
6. 问答只引用这一份合同。合同没写的就说未写明。法规和疾病定义规范以后再加，而且必须带出处，不能覆盖合同原文。
7. 密钥留在环境变量里。模型返回只取 JSON 片段，调用失败要有降级，不能让整份合同没有结果。

这些旧实现不要搬进新版本：车险 5 类关键词、车牌号、六维分数、空的 `contractText`、覆盖式本地存储、单份失败仍提示分析完成、把整份合同一次性塞进章节识别提示词。最后这一条在长条款上既贵又容易超时；新版本应先按目录或规则定位章节，再把必要片段交给模型。
