# 小组合作操作方法

本文给三个人照着做。读完应能独立完成：第一次拿到仓库、领一件任务、在自己的分支上写、别人先合并后把自己的进度接上、用 Pull Request 交回去。

三份文档各管一件事，不要混用：

| 文档 | 管什么 |
|------|--------|
| `重疾险条款风险批注工具-整合方案.md` | 产品是什么、做到哪一步算完成 |
| `三人分工与并行工作手册.md` | 工程、产品、算法各交什么 |
| 本文 | 这些交付如何通过 GitHub 同步 |

角色就三个。**工程**负责网页和解析流水线。**产品**负责白话、风险句、禁语、理想批注，以及什么算隐性限制。**算法**负责切分、规则、金标和第一层召回。当前阶段是整合方案里的第一阶段：上传、性质提醒、条款索引、第一层批注。不做问答。

---

## 1. 每天遵守的四条

1. `main` 上的网页始终能在浏览器里打开。主路径是：上传 PDF → 扫描件或解析失败就显示失败 → 像重疾险合同就看到批注和条款索引，点一条能展开原句。
2. 一个人同一时间只做一个分支，分支只做任务看板上的一行，做完就合并，寿命一般是一两天，不超过一周。
3. 谁都不直接把提交推上 `main`。改动先进自己的分支，再经 Pull Request 合并。
4. 下一行任务能不能开工，只看它自己的前置有没有完成。不等本阶段所有人全部做完。

第一阶段、第二阶段是验收日，用来对照整合方案检查「这一截做完了没有」。阶段结束不是发令枪。

合并变乱，来自两种做法：分支挂了两三周不合并；两个人同时改同一个文件的同一段。Git 可以同时基于同一版开发。分支短、文件事先分开，别人合并后你要做的只是把增量接进来，不是把自己的功能重做一遍。

## 2. 第一次：工程把仓库建起来

下面整段只做一次。产品和算法等工程把仓库地址发到群里再开始第 3 节。

### 2.1 准备账号和工具

1. 三人都注册 GitHub 账号，把用户名发到群里。
2. 三台电脑都安装 [Git](https://git-scm.com/download/win)。安装时路径和编辑器保持默认即可。
3. 安装结束后打开 PowerShell，执行 `git --version`，能看到版本号即成功。
4. 每台电脑执行一次（把名字和邮箱换成自己的 GitHub 信息）：

```powershell
git config --global user.name "你的名字"
git config --global user.email "你的GitHub邮箱"
git config --global core.autocrlf true
```

最后一行让 Windows 和 macOS 的换行符不要变成整文件冲突。

### 2.2 在 GitHub 上建私有仓库

1. 打开 GitHub → New repository。
2. 仓库名例如 `ainsurance`。Visibility 选 **Private**。
3. 不要勾选 “Add a README”。本地已经有文件，勾了会让第一次推送对不齐。
4. 建好后打开 Settings → Collaborators，把产品和算法加为 **Write**。两人接受邮件或网页上的邀请后才拉得到代码。

### 2.3 第一次提交前放上根目录的忽略清单

在仓库根目录新建 `.gitignore`，内容如下。这样依赖包、本机配置和密钥文件不会进仓库。

```gitignore
node_modules/
**/node_modules/

.DS_Store
Thumbs.db
Desktop.ini
*.log

.env
.env.*
```

提交前再检查两处：

- 模型密钥只放在工程机器的环境变量或未入库的 `.env` 里。不要写进源码、文档、表格或聊天记录。
- 未脱敏的评测合同 PDF 不进仓库。原件放群文件或网盘；仓库里的 `评测集/清单.md` 只写文件名、结构特点和谁保管原件。`docs/资料/` 里已经收录的公开白皮书和论文可以入库。

### 2.4 把现有文件推上去

在 PowerShell 中执行（路径按自己的电脑改）：

```powershell
cd "d:\work\26fw\ainsurance pt2"
git init
git add .
git status
```

`git status` 里如果出现 `node_modules`、`.env`、带密钥的文件或未脱敏 PDF，不要继续。先补进 `.gitignore`，再执行一次 `git add .`。确认干净后：

```powershell
git commit -m "纳入产品说明和协作文档"
git branch -M main
git remote add origin https://github.com/你的用户名/ainsurance.git
git push -u origin main
```

地址以 GitHub 仓库页面上的为准。推送时按提示用浏览器登录 GitHub。仓库里目前是文档，网页代码从第一阶段的任务分支加进去。

### 2.5 约定谁可以合并进 main

在 GitHub 仓库 Settings → Branches（或 Rules）里，如果能给 `main` 加上「禁止直接推送、必须走 Pull Request」，就打开。

设置项打不开也按同一条约定执行：禁止 `git push origin main`。代码类 Pull Request 由工程合并；纯文档、表格、规则清单由另一位成员看过即可合并。提交人自己不点合并按钮。

## 3. 产品和算法第一次拿到仓库

工程把仓库地址发到群里，并且确认两人已经接受协作邀请。各自在自己的电脑上：

```powershell
cd D:\work
git clone https://github.com/工程的用户名/ainsurance.git
cd ainsurance
```

之后每天开始做事前，先进入这个文件夹。不要各自拷贝一份压缩包传来传去。

网页跑起来之后，三个人都可以在本地打开、上传同一份评测 PDF。没有密钥时，规则和条款索引可以在本地看结果。需要调用模型的步骤只在工程机器上配置密钥。

## 4. 任务看板：唯一的开工依据

在仓库里维护 `任务看板.md`，和代码一起走 Pull Request。群里口头说的任务，当天补进这张表，否则视为没排期。

每一行只有一个负责人、一件事。表格用下面的列：

| 阶段 | 任务 | 负责人 | 前置 | 会改的文件 | 完成的样子 | 状态 | 分支 |
|------|------|--------|------|------------|------------|------|------|
| 第一阶段 | 上传失败不得显示分析完成 | 工程 | 无 | 上传与解析所在目录，开分支时写明 | 扫描件和解析失败都显示失败原因 | 进行中 | `p1/upload-fail-is-fail` |
| 第一阶段 | 找齐 3 份脱敏重疾条款并写清单 | 产品 | 无 | `评测集/清单.md` | 清单里有文件名和结构差异，原件在网盘 | 未开始 | |
| 第一阶段 | 记录 3 份条款里「第X条」切错的位置 | 算法 | 评测集清单已合并 | `评测集/切分错例.md` | 每份至少写出错在哪一节，并标出没有条号的定义章节 | 未开始 | |

状态只用四个词：**未开始**、**进行中**、**评审中**、**已合并**。

开工前看自己那一行的「前置」：

- 前置是「无」：可以从最新的 `main` 开分支。
- 前置是另一行：那一行变成「已合并」再开。
- 前置是一份文档：那份文档已经在 `main` 上。

一个人不要同时领两行进行中的任务。当前行合并之后，再领下一行。下一行属于后面的小步骤也可以领，只要它的前置已经满足。别人还在写的、和你无关的行，不构成等待。第二阶段的问答、两份合同对比、理赔材料清单，不在当前看板上开行。

共同接口变了必须先改文档再改代码。批注一条的字段以 `三人分工与并行工作手册.md` 第 3 节和整合方案第 11 节为准，包括 `clauseId`、`quote`、`plain`、`riskLevel`、`riskReason`、`visibility`、`benchmark`、`layer`、`confidence`、`needsReview`。要增删字段时，单独开一个文档分支先改这两处，合并之后另外两人再按新字段做。不要在功能分支里私自改字段名。

## 5. 领到一行之后怎么做

下面是日常循环。例子用工程的上传任务，产品和算法把「改代码」换成「改自己那份 Markdown 或表格」，命令相同。

### 5.1 从最新的 main 开分支

```powershell
git switch main
git pull
git switch -c p1/upload-fail-is-fail
```

分支名用 `p1/这件事` 或 `p2/这件事`，全小写，单词用英文短横线，让人从名字能看出看板哪一行。例如：

- `p1/eval-pdf-list`（产品）
- `p1/split-error-notes`（算法）
- `p1/annotation-mock-ui`（工程，用假数据排批注列表）

开分支的同时，把看板那一行改成「进行中」，填上分支名。看板改动可以和这件事放在同一个分支里。

### 5.2 只改这一行点名的文件

做到一半就可以提交，一天至少提交一次。提交说明写这一笔解决了什么，用中文一句：

```powershell
git add 你改过的文件
git commit -m "上传失败时不再显示分析完成"
```

`git add` 写具体文件，不用 `git add .`，避免把本机临时文件一并提交。提交前再看一眼 `git status`。

只在自己的分支上推送：

```powershell
git push -u origin HEAD
```

第一次推这个分支需要 `-u`，之后在同一分支上 `git push` 即可。

### 5.3 用 Pull Request 交回去

1. 打开 GitHub 上这个分支，点 **Compare & pull request**。
2. 标题与看板上的任务名一致。
3. 正文固定三段：
   - 做了什么
   - 别人怎么检查（文档写「看哪一节」；网页写「浏览器里点哪几步」）
   - 动了哪些文件，是否碰到共同字段
4. 右侧 Reviewers 指定另一人。代码请工程看；白话、禁语和理想批注请产品看；规则和金标请算法看。跨角色的改动两人都可以看。
5. 看板状态改为「评审中」。

审查的人只看三件事：有没有超出这一行的范围、完成的样子是否达到、会不会让 `main` 上的网页打不开或把字段改得对不上。通过后由第 2.5 节规定的人点 **Merge pull request**。全组统一用普通 **Merge**。

合并后：

1. 看板那一行改为「已合并」，可以在说明里写合并日期。
2. 删除远程分支（GitHub 合并按钮下方有 Delete branch）。
3. 作者在本地回到 main 并更新：

```powershell
git switch main
git pull
git branch -d p1/upload-fail-is-fail
```

下一行任务重新从最新的 `main` 执行 5.1，不要在旧分支上接着做下一件事。

## 6. 我还在写，别人已经合并了

分两种情况。

### 6.1 别人只是把自己的分支 push 了上去

你的文件夹不会有任何变化，继续写。对方的提交还在对方分支上，没有进 `main`，也不该进你的分支。

### 6.2 别人的 Pull Request 已经合并进 main

你不必立刻停下来，也不必重新克隆仓库，更不必把自己写了一半的功能删掉重做。

选一个能停的点再接：这段逻辑写完、当天收工、或者准备提 Pull Request 之前。一天接一次就够。

先把自己手头的修改提交到自己的分支，避免接的过程中和未保存的内容缠在一起：

```powershell
git add 你改过的文件
git commit -m "批注列表先用假数据排到等待期一条"
git fetch origin
git merge origin/main
```

然后分三种结果：

**自动拼好了。** 两人改的是不同文件，或同一文件里不相邻的位置。Git 直接成功。你原来的提交都在。打开项目继续写。代码改动在浏览器里再打开一次，点一遍自己这条任务，并点一遍主路径确认还能走通。文档改动读一遍自己的那一节即可。

**和你无关。** 例如你在改批注页面，对方改的是理想批注或 `评测集/` 里的金标。合并后多出来的是你没碰过的文件，不必把对方的功能重新做一遍。

**标出了冲突。** 只有两人改了同一处才会发生。Git 会在文件里留下标记：

```text
<<<<<<< HEAD
你写的那几行
=======
main 上对方写的那几行
>>>>>>> origin/main
```

打开该文件，保留最终应该存在的内容，删掉 `<<<<<<<`、`=======`、`>>>>>>>` 这三行标记。然后：

```powershell
git add 冲突的文件
git commit -m "接上 main 上的上传失败提示"
```

不确定该留哪边时，在群里问改那几行的人，不要猜。解决完用自己原来的方式再确认一遍你的功能还在。

有一种情况要提前接，不等到收工：对方在群里说明「批注字段变了」或「你正在用的函数参数变了」。这时在下一个停顿点立刻执行上面的 `fetch` 和 `merge`，按新约定往下写。

群里需要通知的只有两件事：

- 你改了第 4 节列出的批注字段，或改了解析结果的结构。
- 你的任务是别人看板上的前置，并且已经合并进 `main`。

其余合并不必叫全组立刻拉取。

## 7. 怎样让「接 main」几乎不用调试

同一周的文件所有权如下。自己的任务若必须改到别人的目录，先在周五或群里说一声，把看板「会改的文件」写清楚，再开分支。仓库里还没有网页代码时，工程新建目录，并在看板写明路径，不要把代码放进 `docs/md文档/`。

| 角色 | 平时改这些 | 不要同时改 |
|------|------------|------------|
| 工程 | 上传、解析、批注和条款索引的页面与程序 | 产品定稿的白话和禁语；算法定稿的金标对错 |
| 产品 | `docs/md文档/` 里的句式、理想批注、禁语；`评测集/清单.md` | 解析程序 |
| 算法 | `评测集/` 里的规则清单、金标、错例 | 页面文件 |

规则先写在 `评测集/` 的文档里，由工程接进解析程序。这样规则和页面不会在同一周被两个人改。若算法后来直接改解析程序里的规则，那一周工程就不要改同一文件。

工程用假数据排批注列表时，字段必须和手册第 3 节一致。算法稍后接上真实结果时，工程只替换数据来源。

## 8. 周五同步时怎么对看板

固定 30–45 分钟，只对交货。每人回答四句：

1. 我名下哪一行已经合并，哪一行还在进行中。
2. `main` 上现在能点通什么，或文档里新增加了哪一节。
3. 下周我要开的分支会改哪些文件。
4. 有没有人的前置被我堵住了。

当场改 `任务看板.md`，用一个专门的小分支提交，例如 `board/week-3`。不要在周五会上新开功能讨论。范围以整合方案为准，新想法先写成看板里状态为「未开始」的一行，不塞进本周分支。

某人提前做完、下一行又被别人堵住时，按分工手册转到不依赖页面的交付：产品写 2020 版规范病种和合同用语的对照表；算法继续扩金标。这些也是看板上单独的行，同样走分支和 Pull Request。

## 9. 密钥和评测导出

- 模型密钥只在工程的电脑上。产品和算法不要索要密钥，也不要把密钥贴进文档、表格或聊天记录。
- 工程每周把评测合同的导出放进 `评测集/导出/` 或发给算法。导出含条款编号、正文、当前命中的规则、抽到的原句。没有这份导出，算法那一行就不要标成进行中。
- 若发现密钥曾经被写进某次提交：立刻更换密钥，再开一个分支把文件改回不含密钥的版本。只删本地文件不够，旧提交里仍然能看到。

## 10. 操作做错了

**还没提交，发现自己在 `main` 上改。** 不要在 `main` 上继续写。把改动带到新分支：

```powershell
git switch -c p1/你的任务名
git add 你的文件
git commit -m "说明"
```

然后按第 5 节推送这个新分支。本地 `main` 若因此多出了尚未推送的提交，在确认提交已经在新分支上之后停下来问工程，不要自行 `push origin main`。

**已经提交了 `node_modules` 或不该进仓库的文件。** 停止继续推送。把对应规则补进 `.gitignore`，再从仓库索引里去掉该文件夹、保留电脑上的原文件：

```powershell
git rm -r --cached node_modules
git commit -m "停止跟踪依赖目录"
```

**冲突标记忘了删就提交了。** 搜索 `<<<<<<<`，删掉标记并保留正确内容，再提交一次。

**想放弃本地还没提交的修改。** 先 `git diff` 看清楚会丢掉什么。确认之后才对单个文件执行 `git checkout -- 文件路径`。不要对整个仓库使用会丢历史的命令。

## 11. 从领任务到合并，串起来看

```text
更新 main
  → 看板确认前置已完成
  → 从 main 开一行一分支
  → 只改该行点名的文件，当天提交并推送自己的分支
  → 别人若已合并进 main：在停顿点 fetch + merge，只复测交界处和主路径
  → 提 Pull Request，另一人审查
  → 合并进 main，删除分支，看板改为已合并
  → 下一行重新从 main 开始
```

阶段验收单独做一次：该阶段看板上要演示的行都已合并后，工程按整合方案第一阶段的验收标准，在浏览器里走通一遍，把结果写进当周看板。验收有两条：抽出的每条都能对上原句；三份脱敏合同上，第一层金标的召回可以数出来。验收没过，就补一行「未开始」的缺口任务分给对应的人。其余人继续做前置已经满足的下一行。
