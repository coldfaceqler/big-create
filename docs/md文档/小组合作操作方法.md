# 小组合作操作方法

把本文交给协助开发的 AI。AI 读完后带用户操作，不要把全文一次贴给用户。一次只做当前这一步，做完确认结果，再进入下一步。

产品以 `docs/md文档/重疾险条款风险批注工具-整合方案.md` 为准。谁交什么以 `docs/md文档/三人分工与并行工作手册.md` 为准。现在做哪一行以 `docs/md文档/任务看板.md` 为准。

当前只做第一阶段：上传 PDF，失败就显示失败；像重疾险合同的，给出第一层批注和条款索引。不做问答，不做两份合同对比，不做理赔材料清单。

角色是工程、产品、算法。开始前先问用户是哪一个。仓库主人负责工程。批注字段以整合方案第 11 节为准，不私自增删。

## 1. AI 每次怎么说话

- 用中文，先说这一步要做什么，再给要执行的命令或要发出的原文。
- 用户没确认上一步的结果之前，不跳到下一步。
- 命令用 PowerShell。工作目录是仓库根目录。已有本地仓库的人用 `d:\work\26fw\ainsurance pt2`，新克隆的人用他自己的 `big-create` 文件夹。
- 不代替用户在群里发消息。把要发的文字写出来，让用户复制到小组群。
- 不把模型密钥、未脱敏合同写进文件或对话记录。
- 不执行 `git push origin main`。合并只通过 GitHub 上的 Pull Request。
- 看板之外的想法先写成一行「未开始」，不塞进正在做的分支。

## 2. 新的一天，或要开始一行新任务

按这个顺序说，不要颠倒。

1. 请用户打开小组群，看队友在上次分开之后发了什么。逐条问清楚：有没有人说批注字段变了，有没有人说某行已经合并，有没有人说导出已经放好。
2. 有人说字段变了：先不要开新功能。让用户在仓库里执行第 6 节，把 `main` 拉下来，再打开整合方案第 11 节和分工手册第 3 节，对着新字段看。
3. 没有上述消息：打开 `docs/md文档/任务看板.md`。只把这个用户角色下、状态不是「已合并」的行念出来。
4. 让用户选定一行。检查「前置」列。前置不是「无」，且对应的行还不是「已合并」，就告诉用户今天不能做这行，改选一行前置已经满足的。
5. 这个用户已经有一行「进行中」时，不另开一行。先问那一行做到哪了，按第 4 节或第 5 节继续。
6. 选定新行之后，才进入第 4 节。

对用户可以这样开口：「先看群里队友有没有新消息。有人改了字段或合并了任务，我们先处理那个。没有的话，再打开任务看板，从你名下还没合并的行里选一件。」

## 3. 第一次在自己电脑上拿到仓库

工程的电脑上如果已经有 `d:\work\26fw\ainsurance pt2`，跳过克隆，从第 2 节开始。

产品和算法，以及在新电脑上开工的人：

1. 确认已经接受 GitHub 邀请。没接受会克隆失败。
2. 安装 [Git](https://git-scm.com/download/win)。在 PowerShell 里执行 `git --version`，看到版本号再继续。
3. 只在这台电脑上执行一次，名字和邮箱换成自己的 GitHub 信息：

```powershell
git config --global user.name "你的名字"
git config --global user.email "你的GitHub邮箱"
git config --global core.autocrlf true
```

4. 克隆：

```powershell
cd D:\work
git clone https://github.com/coldfaceqler/big-create.git
cd big-create
```

5. 克隆成功后，回到第 2 节，不要直接开始写文件。

## 4. 领到一行之后

先说这一行的任务名、要改的文件、完成的样子。再执行命令。

### 4.1 从最新的 main 开分支

```powershell
git switch main
git pull
git switch -c p1/upload-fail-is-fail
```

分支名换成这行任务的英文短名，用 `p1/这件事`。例如 `p1/eval-pdf-list`、`p1/layer1-rules`。

然后改看板：这一行状态改为「进行中」，填上分支名。看板改动和这行任务放在同一个分支里。

### 4.2 只改这一行点名的文件

一天至少提交一次。说明用中文一句：

```powershell
git add 你改过的文件
git commit -m "上传失败时不再显示分析完成"
git push -u origin HEAD
```

第一次推这个分支用 `-u`，之后用 `git push`。用具体文件名，不用 `git add .`。提交前看 `git status`，确认没有 `.env` 和未脱敏 PDF。

### 4.3 提 Pull Request

让用户打开 GitHub 上这个分支，点 **Compare & pull request**。标题用看板任务名。正文写三段：做了什么；别人怎么检查；动了哪些文件，有没有改批注字段。

审查人：代码请工程看，白话和理想批注请产品看，规则和金标请算法看。提交人自己不点合并。代码由工程点 **Merge pull request**，用普通 Merge。文档和表格由另一位看过的人合并。

合并后让用户执行：

```powershell
git switch main
git pull
git branch -d p1/upload-fail-is-fail
```

把看板那一行改为「已合并」，分支名可以留着备查。下一行重新从第 2 节开始，不在旧分支上接着做。

### 4.4 做完或收工时，让用户发到群里

没合并也可以发。把下面空格换成本次的事实，整段交给用户复制：

```text
今天做了看板这一行：
状态：进行中 / 已提 Pull Request / 已合并进 main
分支：
改了这些文件：
批注字段有没有变：没有 / 变了，请大家先拉 main
谁可以开始下一行：
没做完的话，卡在：
```

字段变了，或者这行是别人的前置并且已经合并，这两句必须出现。其余进展也发，避免队友按旧文件继续做。

## 5. 工作做到一半，队友已经合并

先让用户看群消息，确认对方是只推了自己的分支，还是已经合并进 `main`。

只推了分支：用户的文件夹不会变，继续写。

已经进了 `main`：不必立刻停，也不必重新克隆。写到一个能停的点再接，一天一次。对方说字段变了，则在下一个停顿点马上接。

```powershell
git add 你改过的文件
git commit -m "先提交手头的批注列表"
git fetch origin
git merge origin/main
```

自动拼好了：继续自己的任务。网页改动在浏览器里点一遍自己这条，再点一遍上传和批注。文档改动读一遍自己改的那一节。

两人改了同一处：打开文件，留下最终内容，删掉 `<<<<<<<`、`=======`、`>>>>>>>`。然后：

```powershell
git add 冲突的文件
git commit -m "接上 main 上的更新"
```

不确定留哪边时，让用户把冲突的那几行发到群里问写的人，不要猜。

接完 `main` 之后，如果字段变了，再发一次第 4.4 节的消息，写明「我已接上 main」。

## 6. 只更新 main，不开新任务

用户只是想把别人的合并拿下来时：

```powershell
git switch main
git pull
```

有未提交的修改时，不要在脏的工作区里拉取。先按第 5 节提交到自己的分支，再在那个分支上 `git fetch origin` 和 `git merge origin/main`。

## 7. 周五对看板

用 30 到 45 分钟。AI 让用户按这四句在群里或会上说：

1. 我名下哪一行已合并，哪一行还在进行中。
2. 网页现在能点通什么，或文档新加了哪一节。
3. 下周我要改哪些文件。
4. 有没有人的前置被我堵住了。

会上不发明新功能。新想法写成看板里的「未开始」。会后用 `board/week-1` 这种分支提交看板。

## 8. 文件不要撞车

| 角色 | 改这些 | 不要同时改 |
|------|--------|------------|
| 工程 | 上传、解析、批注和条款索引的程序 | 产品定稿的白话；算法定稿的金标 |
| 产品 | `评测集/清单.md`、`评测集/性质提醒用语.md`、`评测集/理想批注.md` | 解析程序 |
| 算法 | `评测集/第一层规则.md`、`评测集/切分错例.md`、金标 | 页面文件 |

规则先写在 `评测集/`，工程再接进程序。工程用假数据排版时，字段与分工手册第 3 节一致。

密钥只放在工程电脑的环境变量或未入库的 `.env`。评测合同的原件不进仓库。工程每周把条款编号、正文、命中规则、抽到的原句放到 `评测集/导出/` 或发到群里。没有这份导出，算法的「切分错例」不要标成进行中。

## 9. 操作做错了

**还没提交，发现自己在 `main` 上改。**

```powershell
git switch -c p1/你的任务名
git add 你的文件
git commit -m "说明"
```

然后按第 4.2 节推送这个新分支。不要 `git push origin main`。

**提交了 `node_modules` 或不该进仓库的文件。** 先停止继续推送。补进 `.gitignore` 后：

```powershell
git rm -r --cached node_modules
git commit -m "停止跟踪依赖目录"
```

**冲突标记忘了删。** 搜索 `<<<<<<<`，删掉标记，再提交一次。

**想丢掉还没提交的修改。** 先看 `git diff`。确认之后只对单个文件执行 `git checkout -- 文件路径`。

密钥如果已经进了某次提交：让用户更换密钥，再开分支把文件改回不含密钥的版本。只删本地文件不够。

## 10. 一轮做完时 AI 自己核对

结束前对照这张单，缺哪项就补哪项，不要假设用户已经做了。

- 群里的新消息看过了。
- 看板那一行的状态和分支名是对的。
- 改动在自己的分支上，不在直接推送的 `main` 上。
- 该发的收工消息已经写给用户复制。
- 没有密钥和未脱敏 PDF。
- 如果这行已经合并，用户本地已经回到最新的 `main`。
