项目简介
本项目致力于构建面向普通消费者的保险条款理解工具，产品形态为微信小程序。用户上传保险合同PDF后，系统自动完成文本提取、条款切分与结构化分类，按"保障责任""免责责任""理赔条件""投保须知"等类别归集展示，并支持基于合同原文的自由问答——用户可针对上传合同进行提问，系统基于合同内容生成回答。项目当前已具备可运行的小程序原型，端到端链路（PDF上传→云端解析→条款分类→交互问答）已部署上线。技术方案采用"本地微调小模型主分类 + 大模型API兜底 + 人工标注回流"的混合策略，以控制长期推理成本并保证分类准确率的持续提升。产品边界明确：不涉保险产品推荐、不引导品牌选择、不介入核保理赔，专注合同理解这一垂直环节。商业模式上，C端全免费以聚拢用户积累标注数据，B端面向保险教育与内容平台提供合同解析API，按调用量计费。

项目选题（项目来源、拟开发或已开发的产品/服务的行业背景、功能说明）
项目选题源于团队成员的切身经历。在购买保险产品时，一份合同动辄数万字，充斥"近因原则""代位求偿""免赔额与免赔率"等专业术语，即便逐字通读仍难以完整把握保障边界和潜在免责条款。这一痛点具有普遍性：行业投诉数据和企业消费者调研均反复指出，"条款告知不清晰""责任解释不到位"是保险消费纠纷的主要诱因。因此，本项目选择"合同条款可解释化"作为产品创新切入点，从普通消费者的认知视角构建技术与产品方案。
从行业背景来看，保险消费市场存在三重结构性矛盾。其一，保险消费总量持续增长，特别是年轻群体首次投保比例显著上升，但消费者的保险知识储备明显滞后于购买意愿。其二，传统保险服务链路在售前环节有代理人讲解和比价工具，但合同到手后的核心理解环节是断裂的——用户被要求自行消化数十页合同文本。其三，大模型技术驱动智能客服在保险行业快速铺开，但保险合同场景对输出准确性有刚性约束：一次错误回答可能导致真实经济损失，而通用大模型缺乏针对保险条款的专业微调，在特定条款的判定边界上容易出现概括性偏差或幻觉。基于上述分析，市场需要的是专为保险合同理解设计的产品，而非通用问答工具加挂保险前缀。
在功能方面，当前已完成的核心能力包括：微信小程序内的合同PDF上传与云端处理、文本提取与条款单元切分、按类别自动归类展示、基于当前合同的自由问答、通用保险知识问答、用户画像问卷与合同收藏管理。下一阶段拟开发的核心能力包括：本地部署的小模型分类引擎，对大模型API预标注数据进行监督微调，实现低置信度兜底与人工纠错回流；三级层级化的条款分类体系（大类别→子类别→判定规则），每个分类节点绑定原文证据句；多合同差异化对比分析，上传两份同类产品条款后系统自动标注保障范围、免责条款、理赔条件的差异项；面向参赛评审的完整产品展示与可行性论证页面。

创业基础与可行性（国内外相关产品/服务的发展现状述评）
从技术演进路径来看，国外保险科技大致经历了渠道数字化、流程智能化、决策可解释化三个阶段。承保和理赔领域的自动化已趋于成熟，而当前的前沿方向正转向"可解释化"——监管和消费者同时要求AI参与的保险决策具备可理解性和可追溯性。本项目切入的合同可解释化方向，正处于这一趋势的起点，目前市场上尚无广泛应用的合同可解释化垂直产品，存在窗口期。
国内与合同理解相关的产品服务，可归为三类，各有其技术层面的能力边界。第一类是通用AI问答工具，这类产品基于大语言模型的通用能力，能够上传PDF并生成问答，但在保险条款场景下存在系统性缺陷：其一，通用预训练语料中保险专业文本占比极低，模型在区分"保障责任"与"免责责任"的语义边界时缺乏领域知识，容易出现跨类别混淆；其二，当前主流大模型采用Transformer架构的自回归生成机制，在处理长文本（保险合同动辄数万tokens）时存在位置编码衰减和注意力分散问题，对合同后半部分的条款细节容易遗漏或概括失真；其三，通用模型无法提供精确的原文证据句溯源，因为其输出是概率分布驱动的token生成而非检索增强的精准引用。第二类是保险科普类内容平台，其内容依赖编辑人工撰写，无法针对用户上传的个性化合同生成实时交互式分析，本质上属于静态信息分发而非动态推理。第三类是保险公司自有服务入口，其条款展示和智能客服功能天然服务于本品牌产品的销售转化目标，输出立场的独立性难以保障，且不支持跨保险公司、跨产品的条款横向对比。
上述三类产品的功能空白交集，指向一个共同的技术需求：一个不依附于任何保险品牌、具备领域知识微调、能输出原文证据链的合同理解工具。这恰恰是本项目的差异化定位。
从技术层面深入分析，本项目与上述通用方案的差异根植于底层模型策略。通用AI工具调用的是未经领域微调的大模型。大模型的训练语料以互联网通用文本为主，保险条款中的法律表述、排除性条款、分层免赔逻辑等在通用语料中属于长尾数据，模型对此类专业语义的学习远不充分。此外，大模型API存在调用成本高（每次推理数百至数千tokens）、响应延迟不稳定、无法本地化部署等工程层面的约束。本项目采用的技术路径是：针对保险条款分类任务，构建领域标注数据集，对轻量级预训练模型（0.5B-1.5B参数规模）进行监督微调，使模型在特定的保险条款分类子任务上达到甚至超越通用大模型的领域准确率，同时将单次推理成本降至极低水平（本地CPU/GPU推理），并在小程序端实现毫秒级的分类响应。这种策略在学术上属于"领域适应与模型压缩"的范畴——通过面向特定垂直子任务的知识蒸馏与监督微调，用轻量模型替代庞大通用模型，在保证效果的前提下显著降低部署成本和调用延迟。项目设计了人工标注回流的持续迭代机制：微调模型上线后，低置信度的分类结果将自动路由至大模型API做兜底判断，同时提交人工复核；复核纠错后的样本加入训练集，按月触发增量微调。这个闭环确保了模型在真实分发环境中持续优化，分类准确率预期在持续标注迭代下逐步提升。
在技术可行性之外，还有能力维度的论证。原型层面，现有系统已完成从PDF上传到条款解析、分类、问答的完整链路部署，所有技术组件（文本提取、条款切分、向量检索、大模型问答）基于成熟开源框架与商用API搭建，后续混合分类引擎的引入属于渐进式架构迭代而非推翻重来。数据层面，标注策略分三步推进：先用大模型API对常见人身险条款（重疾、医疗、意外三类，约30-50份合同）进行预标注，快速积累500-800条初始训练样本；两名团队成员交叉复核预标注结果，争议条款通过团队讨论与参考文献仲裁；线上分类错误的案例经人工纠正后纳入下一轮训练集。为弥补团队在保险精算领域的知识短板，项目计划在推进过程中引入校内法学或保险学专业的同学担任顾问。团队层面，三人分工覆盖产品定义与领域知识、算法研发与数据工程、前端开发与部署运维三个必要方向，项目周期按季度里程碑推进。场景层面，每次保险合同购买决策都伴随大量合同阅读需求，是高频常态行为，微信小程序作为承载形式天然具备零安装门槛和社交传播优势。

团队现有基础、知识资源等基础条件
团队目前由三人组成，分工覆盖产品与保险知识、算法与数据工程、前端与小程序开发三个方向。产品与保险方向负责项目的需求分析、产品功能定义、分类体系的设计与标注质量的把控，确保产品的保险场景适配性。算法与数据方向负责模型选型、实验设计与微调方案的制定、评测指标的追踪以及数据管线的搭建，承担从数据处理到模型上线的技术链路。工程与前端方向负责微信小程序的页面开发与迭代、云函数的部署与运维、演示环境的搭建与维护。三个角色的分工覆盖了从产品设计到技术实现到上线部署的完整链路。项目周期为一年，按季度设定阶段性里程碑，当前已完成原型版本的开发与首次系统性代码体检，明确了安全、稳定性与架构优化三条整改路径的优先级。
在现有技术成果方面，小程序端已建立完整的页面流程，涵盖合同上传、条款分类浏览、问答交互、问卷填写与合同收藏等核心用户操作路径。云端基于微信云函数构建了解析与问答的服务链路，用户上传PDF合同后由云函数完成文本提取、条款单元切分与分类归集，同时支持用户基于当前合同文本进行自由提问，系统基于合同内容生成回答，该链路当前已部署上线并可正常运行。此外，向量检索与知识库问答已完成初步接入，系统能够将合同文本转化为向量索引，在用户提问时通过语义检索定位相关条款段落，为问答提供更精确的上下文支持。
工程基础方面，团队维护有持续迭代的代码仓库，采用分支策略管理功能开发与版本发布，代码与项目文档保持同步更新，确保任何阶段均可回溯到历史版本。团队同时具备快速演示与评审反馈的闭环能力——能够在短时间内将当前原型部署至可演示状态，收集反馈后迅速调整优先级并进入下一轮迭代。
现有知识成果方面，团队已完成首轮系统性的代码体检，形成了一份覆盖安全风险、功能缺陷、性能瓶颈等方面的项目分析文档，对各问题按P0（必须立即处理）、P1（短期内修复）、P2（按计划优化）三个优先级进行分级，并制定了对应的整改计划。同时，团队已梳理出面向参赛评审的产品化表达框架，明确了项目在技术论证、市场分析和商业化路径三个维度上的论述逻辑，为申报材料的撰写和后续答辩提供了结构化的基础。
在待补充资源方面，保险法务与精算领域的专业顾问目前尚未到位，团队拟在项目推进过程中引入校内法学或保险学专业的老师担任咨询角色。行业数据合作资源同样处于待拓展阶段，计划通过参赛平台和校内渠道逐步建立联系。长周期的算力与标注预算目前主要依赖校内创新基金的申请和赛事孵化支持，具体额度和分配方案将根据项目进展进一步明确。

市场前景、项目优势、预期效益（市场需求、目标市场、项目优势、预期效益）
从行业数据来看，保险消费投诉中涉及"条款告知不清""责任解释不到位"的占比长期处于高位。据行业公开调研显示，相当比例的保险购买者在投保时未能完整理解合同条款内容，首次投保人群的理解率显著更低。这一结构性矛盾在保险消费需求增长、年轻群体保障意识快速提升但仍普遍缺乏保险知识储备的背景下日趋突出。政策层面，《互联网保险业务监管办法》等法规持续强化销售适当性和信息披露要求，为"可理解、可验证、可追溯"的消费者端服务工具创造了明确的市场空间——保险教育和条款透明化正在从辅助优势转变为行业服务质量的准入条件。
目标市场以C端为主，B端为辅。C端目标用户包括首次投保决策者、家庭保障规划者以及保险知识薄弱的年轻消费群体；国内每年新增保险消费者规模以千万计，其中年轻群体构成了需求和知识落差最大的核心增量市场。B端面向保险教育类内容平台和企业员工福利平台，以标准化合同解析API的形式向合作伙伴提供服务，自身定位于技术工具提供方而不直接介入企业的保险决策环节。市场进入策略为先C端验证产品价值、积累用户和使用数据，在C端场景跑通后将核心解析能力封装成标准化API，向B端合作伙伴进行技术输出。
项目优势集中在五个维度。定位维度，专注合同理解这一垂直环节，不做泛化功能的横向扩张，用户体验路径清晰。可解释性维度，分类结果和问答输出均附带合同原文证据句，所有判断可查证，这一能力依托于本地微调模型与向量检索的结合，具备技术可验证性。成本维度，混合模型架构将主要推理负载由本地微调小模型承担，避免了对大模型API的持续高额调用，月度运营成本被控制在可预测范围内。中立性维度，不绑定任何保险品牌，不输出推荐导向结论，这一产品设计边界是建立用户信任的结构性基础。商业逻辑维度，C端免费引流积累用户和标注数据，数据反哺模型迭代，技术能力通过B端API实现商业转化，形成可正向循环的商业模式。
预期效益可从用户端、行业端和团队端三个层面衡量。用户端一年周期的量化目标方面：合同核心信息理解正确率基线待测，目标提升至百分之八十以上，通过阅读后十题标准测试衡量；典型三十页合同阅读耗时基线待测，目标缩短至十五分钟以内，通过工具使用时长记录衡量；问答满意度目标达到四分以上，通过每次回答后用户星评衡量；用户推荐意愿NPS目标大于二十，通过使用后标准NPS问卷衡量。
行业效益方面，提升消费者在投保决策过程中的信息对称程度，降低因合同理解不足引发的理赔争议概率。项目积累的条款分类与解释技术能力，可复用于保险教育、消费者保护等公益场景。团队效益方面，将形成一套完整的保险条款分类与解释技术资产，为后续产品化提供可复用的模型和标注数据基础；跑通从需求验证、产品落地到商业论证的创业实践全流程，积累多维度的参赛产出成果。
商业模式采用C端免费加B端API收费的基本架构。C端用户享有合同上传解析、条款分类浏览、合同内问答、多合同对比等全部核心功能的完全免费使用权限，每日限额三次合同分析可覆盖日常使用场景，C端是用户增长和标注数据积累的核心引擎。B端面向保险教育平台和企业福利平台等机构客户，提供标准化的合同解析API，按实际调用量计费。第一年成本估算：云函数与存储月均三百至五百元（微信云环境基础套餐），大模型API调用月均二百至五百元（按日活一百人、人均两次兜底调用估算），标注与质检由团队自行承担计入日常工作时间，演示物料一次性约一千元（录屏工具、演示域名等），月均总成本约五百至一千元。
在收入端，参照同类文本解析API的市场价格（每次解析0.5-2元），前六个月以免费试用拓展合作伙伴，第七至十二月预计接入两到三家B端客户，月收入约一千至三千元，可覆盖基础运营成本并实现初步收支平衡。
用户获取策略分阶段推进。冷启动阶段（第一至三月），聚焦校内保险与金融相关院系社群和学生保险咨询场景进行首批种子用户招募，目标获取前五十位种子用户；同时围绕保险合同免责条款、投保常见的理解误区等话题，在校内社交媒体渠道制作科普内容并附带小程序入口。增长阶段（第四至八月），进入微信已有的保险消费者讨论社群和产品对比群组，以工具能力展示带动自然试用；多合同对比功能上线后，用户能一键对比已有保单的保障差异，自然触发亲友分享的传播链路。留存机制上，用户可长期保存分析过的合同，当对应险种的分类体系更新或同类产品出现重要条款变更时，通过推送提醒用户审视已有保障。分阶段用户增长目标：第一至三月注册用户一百至二百人、月活三十至五十人；第四至八月注册用户五百至一千人、月活一百至二百人；第九至十二月注册用户两千至四千人、月活三百至五百人。
在合规层面，保险行业受《互联网保险业务监管办法》等法规严格监管。本项目在产品设计阶段已划定合规边界：仅对合同条款进行可读化呈现与解释，不提供保险产品推荐、不引导购买行为、不介入保费测算与理赔判断——不构成保险中介或保险咨询主体行为。每次问答结果下方标注免责声明，上传合同前弹窗告知数据使用范围。用户上传的合同仅用于当次解析与本人合同管理，不做其他商业用途，用户可随时发起删除，系统内所有日志执行脱敏处理，不存储用户个人识别信息。监管部门对投保环节的信息披露要求与本项目的功能方向一致而非冲突——本项目实际上是监管所要求的"充分信息展示和风险提示"在消费者端的技术化补充。

项目实施要点（生产运营、管理模式、投融资方案、风险防范等）
本项目以"数据—模型—产品"三轮闭环推进研发工作。数据侧，建立标注规范、抽检机制与冲突仲裁规则，确保训练数据的质量和一致性。模型侧，采用小模型主路由承担常规分类任务，低置信度结果自动转至大模型兜底，人工复核后的纠错样本回流至训练集，形成持续迭代的优化回路。产品侧，围绕合同理解这一核心用户路径，持续优化交互体验、分类展示方式与解释表达形式。研发节奏上，采用"季度目标加双周迭代加月度评测"的管理方式，以季度为单位设定阶段性里程碑，每两周进行一次迭代交付与评审，每月开展一次系统性的质量评测。
管理模式方面，团队建立了覆盖产品、研发、质量、文档四个维度的管理规范。产品管理上采用需求池分级机制，将功能需求按必须实现、应当实现、可选实现三个优先级分类，并结合版本路线图进行排期。研发管理上，执行统一的代码规范与分支策略，每个版本交付前通过发布清单逐项确认，并进行回归验证。质量管理上，搭建关键指标看板，持续追踪合同解析成功率、条款分类F1值、问答可用率以及系统故障率等核心指标。文档管理上，技术文档、评测文档和参赛材料三类文档同步维护，确保项目推进过程中的知识沉淀和成果可追溯。
投融资方案方面，当前尚处于项目早期，资金需求和具体来源仍需进一步明确。资金将主要用于云服务和API调用费用、标注质检相关成本、测试与演示物料的制作，以及合规支持等方面。资金来源计划主要包括校内创新基金的申请、赛事孵化支持以及可能的产业合作资源。
风险防范方面，团队从技术、合规和运营三个维度进行了风险评估并制定了应对策略。技术风险包括分类偏差、模型漂移和API服务不稳定，应对措施为设置置信度门控阈值、建立双路由兜底机制、对关键链路配置降级策略。合规风险涉及用户隐私数据处理和模型输出边界不清，应对措施为全量日志脱敏处理、遵循数据最小化原则采集信息、在每次输出结果中附加免责声明并明确能力边界。运营风险包括用户增长速度不及预期和运营成本超出预算，应对措施为先聚焦核心场景验证产品价值、采取分阶段投入控制成本节奏、优先保障高价值功能的稳定性。

进度安排与人员分工
1 总体执行策略
本项目采用 "数据 — 模型 — 产品" 三轮闭环的研发推进模式，以季度为单位设定核心里程碑，每两周进行一次迭代交付与评审，每月开展一次系统性的质量评测。整体执行节奏遵循 "先治理能力，再谈载体迁移" 的原则，优先解决安全、稳定性与架构基础问题，随后聚焦核心技术能力升级，最终完成参赛交付与产品可行性论证。项目全程保持 "只服务个人、帮助读懂并选对保险合同" 的核心理念，不涉及保险产品推荐、品牌引导或核保理赔等超出产品边界的功能。
2 分阶段详细执行计划
2.1 第一季度（1-3 月）：安全整改与基础重构
本阶段核心目标是完成系统安全治理、关键功能缺陷修复以及基础架构优化，为后续技术升级奠定稳定的工程基础。
具体任务与分工：
成员 C（工程与前端）：牵头完成密钥与数据安全治理工作，移除代码与配置中的所有明文 API 密钥，改为环境变量注入方式并完成密钥轮换；制定并实施全量日志脱敏策略，确保合同片段、个人信息及令牌信息不会出现在日志中；增加请求权限校验与数据隔离机制，防止跨用户读取敏感合同数据。修复 "上传失败仍提示成功"" 历史数据被覆盖 " 等 P0 级关键逻辑问题；为所有云函数响应定义统一错误码与前端兜底文案，避免原始错误信息直接暴露给用户；在文件上传、合同解析、问答响应等关键节点增加指标上报能力，实时监控上传成功率、解析成功率、超时率及平均响应时延。
成员 A（产品与保险）：启动保险条款层级分类体系的前期调研与设计工作，梳理保险行业通用的条款分类标准，结合消费者认知习惯确定一级分类与二级分类的初步框架；完成标注手册 v0.1 版本的编写，明确各类条款的定义、边界样例及冲突裁决规则；设计用户反馈收集机制，为后续模型优化提供用户视角的输入。
成员 B（算法与数据）：完成现有分类模型的基线评测，建立包含 Macro-F1、各类召回率、混淆矩阵等指标的模型质量评估体系；搭建基础数据处理管线，实现合同文本提取、条款切分的自动化流程；准备初始标注数据集，筛选 30-50 份常见人身险合同（重疾、医疗、意外三类），为下一阶段的预标注工作做好准备。
关键产出：密钥治理完成报告；所有 P0 级问题关闭清单；统一错误码规范与前端兜底文案；关键节点指标监控看板；分类体系初步框架；标注手册 v0.1；现有模型基线评测报告；初始合同数据集。
里程碑节点：3 月底完成安全整改与基础重构验收，系统稳定性达到 99.5% 以上。
2.2 第二季度（4-6 月）：分类体系与数据体系建设
本阶段核心目标是完成保险条款层级分类体系的最终设计，建立高质量标注数据集，并训练出小模型分类基线。
具体任务与分工：
成员 A（产品与保险）：最终确定 "一级类 - 二级类 - 标签属性" 三级层级分类体系，其中一级类包括保障责任、免责责任、理赔条件、费用与费率、合同效力、争议处理、附加约定等；在一级类下细分二级类，如在 "保障责任" 下细分车损、第三者、人伤、附加险触发条件等；为每条条款设计风险等级、适用人群、触发场景、可解释要点等标签属性。完善标注手册至 v1.0 版本，建立 "保险专业依据 + 语言证据" 双依据标注机制，明确保险利益、损失补偿、最大诚信等专业原理与条款触发词、责任句式、法律术语等文本证据的对应关系；组织团队成员进行标注培训，建立交叉复核与争议仲裁流程。
成员 B（算法与数据）：使用大模型 API 对初始合同数据集进行预标注，快速积累 500-800 条训练样本；与成员 A 共同完成预标注结果的交叉复核，对争议条款进行团队讨论并参考保险专业文献进行仲裁；选择 0.5B-1.5B 参数规模的轻量级预训练模型，基于标注数据集进行监督微调，训练出小模型分类基线；建立固定验证集，每月对模型质量进行评测并输出月度模型质量报告。
成员 C（工程与前端）：完成云函数的架构重构，合并重复的服务能力，收敛无入口或冗余页面；抽象统一服务层，将解析、分类、问答、检索等核心能力封装为标准化接口，形成明确的接口契约；将平台耦合逻辑与领域逻辑解耦，为后续 H5 / 多端复用预留空间；建立最小可持续的质量保障机制，编写分类规则、切分函数、置信度阈值策略等核心模块的单元测试用例。
关键产出：三级层级分类体系 v1.0；标注手册 v1.0；包含 500-800 条高质量标注样本的训练集；小模型分类基线；月度模型质量报告模板；统一服务层接口规范；核心模块单元测试用例集。
里程碑节点：6 月底完成小模型基线训练，分类 Macro-F1 值达到 75% 以上。
2.3 第三季度（7-9 月）：混合方法上线验证
本阶段核心目标是实现 "小模型主分类 + 大模型兜底 + 人工回流" 的混合型分类方法上线，并通过灰度测试验证其效果与稳定性。
具体任务与分工：
成员 B（算法与数据）：设计并实现混合分类路由机制，主路径由小模型执行条款级多分类并输出类别与置信度；设置 0.75 的置信度阈值，低于阈值的低置信度样本自动路由至大模型 API 进行二判；建立人工复核队列，将高风险条款或模型冲突样本提交人工复核；实现模型回流训练机制，将人工复核结果回灌至训练集，按月进行增量微调，持续提升模型稳定性。优化 RAG 检索策略，避免固定小样本截断导致的召回不足问题；引入检索缓存与 Embedding 缓存，减少重复计算与外部 API 调用成本。
成员 C（工程与前端）：完成混合分类引擎的工程化部署，将串行批量调用改为 "限流并发 + 失败重试" 策略，提高系统批处理效率；搭建上传–解析–展示–问答全链路的集成测试环境，每次版本发布前进行全链路回归测试；实现人工复核后台的开发，支持标注人员在线查看、修改分类结果并提交反馈；完善系统监控体系，增加低置信度触发率、人工复核占比、关键风险类漏检率等业务指标的监控。
成员 A（产品与保险）：负责人工复核队列的管理与质量把控，制定复核标准与流程；收集灰度测试用户的反馈意见，优化分类展示方式与解释表达形式；设计多合同差异化对比分析功能的产品方案，明确系统自动标注保障范围、免责条款、理赔条件差异项的具体规则；启动产品说明书与计划书的撰写工作。
关键产出：混合分类引擎上线版本；人工复核后台；灰度测试用户反馈报告；月度模型质量报告（含增量微调效果）；多合同对比功能产品方案；产品说明书初稿。
里程碑节点：9 月底完成混合分类方法灰度验证，整体分类 Macro-F1 值达到 85% 以上，人工复核占比控制在 15% 以下。
2.4 第四季度（10-12 月）：参赛交付与可行性论证完善
本阶段核心目标是完成参赛所需的所有材料准备与产品演示版本开发，同时完善产品可行性论证，形成具备可持续迭代能力的产品基线。
具体任务与分工：
成员 A（产品与保险）：完成终版项目计划书、保险产品设计说明书的撰写；整理项目的市场分析、商业模式、合规论证等内容，形成完整的可行性论证报告；设计面向参赛评审的产品展示页面，突出项目的技术创新点与用户价值；准备答辩演示文稿，梳理项目核心亮点与答辩思路。
成员 B（算法与数据）：完成参赛版本的模型优化，针对评审关注的关键风险类条款（如免责责任）进行专项优化，降低漏检率；整理项目的技术资产，包括模型权重、标注数据集、评测报告等；撰写技术实现文档，详细说明混合分类方法的设计思路与实现细节。
成员 C（工程与前端）：完成参赛演示版本的小程序开发，上线多合同差异化对比分析功能；优化产品交互体验，提升用户操作流畅度；制作产品功能录屏材料，展示从合同上传到条款解析、分类展示、问答交互、多合同对比的完整流程；部署稳定的演示环境，提供小程序访问链接与二维码。
关键产出：终版项目计划书；保险产品设计说明书；完整的可行性论证报告；参赛演示版本小程序；产品功能录屏材料；答辩演示文稿；项目技术资产包。
里程碑节点：12 月初完成所有参赛材料准备与产品演示版本验收，12 月中旬提交参赛申请并准备答辩。
3 日常研发与管理机制
团队建立覆盖产品、研发、质量、文档四个维度的管理规范，确保项目有序推进。产品管理采用需求池分级机制，将功能需求按 "必须实现、应当实现、可选实现" 三个优先级分类，并结合季度路线图进行排期。研发管理执行统一的代码规范与 Git 分支策略，每个版本交付前通过发布清单逐项确认，并进行全链路回归验证。质量管理搭建关键指标看板，持续追踪合同解析成功率、条款分类 F1 值、问答可用率、系统故障率以及低置信度触发率、人工复核占比等核心指标。文档管理要求技术文档、评测文档和参赛材料三类文档同步维护，确保项目推进过程中的知识沉淀和成果可追溯。

项目采用 "先 C 端验证产品价值、积累用户和使用数据，再向 B 端进行技术输出" 的市场进入策略。冷启动阶段（1-3 月）聚焦校内保险与金融相关院系社群和学生保险咨询场景，招募首批 50 位种子用户；围绕保险合同免责条款、投保常见理解误区等话题制作科普内容，在校内社交媒体渠道传播并附带小程序入口。增长阶段（4-8 月）进入微信已有的保险消费者讨论社群和产品对比群组，以工具能力展示带动自然试用；多合同对比功能上线后，利用用户一键对比已有保单保障差异的需求触发亲友分享传播。留存机制方面，支持用户长期保存分析过的合同，当对应险种的分类体系更新或同类产品出现重要条款变更时，通过推送提醒用户审视已有保障。
